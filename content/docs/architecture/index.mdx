The lessons build a small sign-up app. The question it raises is real: where should the code and the data live as the app grows? These pages follow the same app through nine designs. Each has a diagram, when to use it, its trade-offs, and the concept pages to read.

| Design | Fixes | New problem |
|---|---|---|
| [1. Single server](/docs/architecture/1-single-server) | Nothing: the starting point | Data and app die together |
| [2. Database tier](/docs/architecture/2-database-tier) | Data outlives the server | One server is still a single point of failure |
| [3. Scaling](/docs/architecture/3-scaling) | Vertical: a bigger server. Horizontal: more servers | More moving parts, higher cost |
| [4. High availability](/docs/architecture/4-high-availability) | Survives a whole Availability Zone failing | Roughly double the cost |
| [5. Three-tier web app](/docs/architecture/5-three-tier) | Each layer locked to the one in front of it | More networking to set up |
| [6. Static site](/docs/architecture/6-static-site) | No servers for sites that are only files | No server-side code |
| [7. Containers on ECS](/docs/architecture/7-containers) | Same image everywhere, no instances to manage | Images and task definitions to learn |
| [8. Event-driven](/docs/architecture/8-event-driven) | Slow steps no longer make users wait | Harder to trace and debug |
| [9. Serverless](/docs/architecture/9-serverless) | No servers to patch or size; near zero cost when idle | A different programming model |

The [AWS Well-Architected Framework](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html) is the vocabulary for comparing them: reliability, security, cost, performance, operations, sustainability.
