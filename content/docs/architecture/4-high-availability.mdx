High availability means the app keeps running when a part fails. On AWS, the unit of failure to plan for is the Availability Zone: one or more data centres that can lose power or network together. So put at least one copy of every tier in each of two zones.

## What it is

- **Load balancer** across two or more zones. It stops sending traffic to targets that fail health checks.
- **Auto Scaling group** across the same zones. If a zone goes down, it launches replacements in the healthy one.
- **RDS Multi-AZ**: a synchronous standby in a second zone, with automatic failover.
- **Nothing stored on one instance**: the app is stateless, as in [Horizontal scaling](/docs/architecture/3-scaling/horizontal).

## When to use it

Anything people depend on: a club sign-up during an event, a project you show employers, any production app. Not for a one-evening workshop.

## Trade-offs

| | |
|---|---|
| Cost | Roughly double the compute and database, plus the load balancer |
| Complexity | More parts, and failover you should test, not assume |
| Scaling | Same as horizontal scaling: add instances in each zone |

For surviving a whole Region failing, see the Well-Architected disaster recovery guidance. That is a much bigger step.
