The data gets its own home: a database that outlives any one server. This is where [Lesson 1](/docs/web-server-and-rds) and [Lesson 2](/docs/app-to-rds) both end.

## What it fixes

- **The data outlives the server.** Terminate the instance and the sign-ups are still there.
- **The app server becomes stateless.** It holds no data of its own, so you can run more than one copy. That is what makes [3. Scaling](/docs/architecture/3-scaling) possible.
- **Backups and patching are AWS's job.** RDS takes automated backups and patches the engine.

## Which database

Relational (RDS or Aurora) for data with a fixed shape and SQL; NoSQL (DynamoDB) for lookups by key at any scale; a cache (ElastiCache) in front when reads repeat. See [Databases](/docs/concepts/databases).

## Trade-offs

| | |
|---|---|
| Cost | Adds an RDS instance, billed by the hour while it exists |
| Complexity | One more resource, a connection string, a password to keep safe |
| Scaling | The database can grow on its own; the app is still one server |

## What is still fragile

- One EC2 instance. If it stops, the site stops.
- The database password sits in a `.env` file on the server. AWS Secrets Manager with an IAM role is the next step.
