In the earlier designs, every step happens inside one request: the user waits while the app saves, emails and counts. In an event-driven design, the app records what happened and returns. Other parts react in their own time.

## The three AWS building blocks

| | Amazon SQS | Amazon SNS | Amazon EventBridge |
|---|---|---|---|
| Model | Queue: consumers pull messages | Pub/sub: pushes to every subscriber | Event bus: rules match events and route them |
| Keeps messages | Yes, until processed (up to 14 days) | No, delivers in real time | No, retries delivery for up to 24 hours |
| Use it for | Buffering work, smoothing spikes | One event, many receivers | Routing events between services and SaaS apps |

They combine: SNS to fan out, SQS to buffer each receiver, as in the diagram.

## When to use it

- A slow step (emails, image processing, reports) should not make the user wait.
- One event, several things to do.
- Traffic spikes: the queue absorbs them and workers catch up.

## Trade-offs

| | |
|---|---|
| Cost | Pay per message; very low at club scale |
| Complexity | Harder to follow and debug: work happens later, somewhere else |
| Scaling | Each consumer scales on its own |

Messages can arrive more than once, so each consumer must cope with duplicates.
