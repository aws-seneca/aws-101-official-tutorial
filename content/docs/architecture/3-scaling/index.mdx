The app now keeps its data in a database. The next problem is load: one server can only do so much. There are two ways to add capacity.

| | [Vertical scaling](/docs/architecture/3-scaling/vertical) | [Horizontal scaling](/docs/architecture/3-scaling/horizontal) |
|---|---|---|
| What you do | Change to a bigger instance type or DB instance class | Run more instances and spread traffic across them |
| Code changes | None | The app must be stateless: no data or sessions on the server |
| Downtime | A short outage while the instance restarts | None, if done right |
| Limit | The biggest instance type | Much higher |
| Survives a server failing | No, there is still one server | Yes, the others keep serving |

## Which one first

Start vertical: it is one setting and no code change, and it buys time. Move to horizontal when you need to survive a server failing, when traffic swings through the day, or when the biggest instance is not enough.

Databases scale both ways too. A bigger DB instance class is vertical. Read replicas, which take read traffic off the primary, are horizontal.
