---
title: Horizontal scaling
description: More instances behind a load balancer, added and replaced automatically. Read replicas for the database.
---

Horizontal scaling, or scaling out, means running more copies of the app and spreading traffic across them. If one fails, the others keep the site up.

```text
Browser ──> Application Load Balancer ──> Auto Scaling group
                                            ├─ EC2 (AZ a)
                                            └─ EC2 (AZ b)  ──> RDS (Multi-AZ)
```

## The parts

- **Application Load Balancer (ALB).** One address for the whole site. It sends each request to a healthy instance and stops sending to one that fails its health check.
- **Auto Scaling group.** Keeps a set number of instances running. You give it a minimum, a maximum and a desired count. It replaces instances that fail health checks, and with a scaling policy it adds instances when load goes up and removes them when it drops.
- **Launch template.** The recipe for each new instance: AMI, instance type, security group, and user data that installs and starts the app. New instances must come up ready with no one logging in.
- **Two or more Availability Zones.** Spread the instances so one data centre going down does not take the site with it.

## The rule: the app must be stateless

Any instance can get any request, and any instance can be replaced at any time. So nothing that matters can live on one instance's disk or memory:

- **Data** goes in the database. [2. Databases](/docs/architecture/2-databases) is what makes this design possible.
- **Sessions** go in the database or a cache such as [ElastiCache](/docs/architecture/2-databases/caching), not in server memory.
- **Uploaded files** go in Amazon S3, not on the instance.

The Lesson 2 app already passes this test once it uses RDS: the sign-ups live in the database, not on the server.

## The database side: read replicas

The database is often the next bottleneck. An RDS **read replica** is a read-only copy of the database, kept up to date from the primary. Send reads to replicas and writes to the primary.

- Replication is asynchronous, so a replica can lag a little behind. Read from the primary when you need what was just written.
- Read replicas spread read load. They are not the same as Multi-AZ, which is a standby for failover.
- Writes still go to one primary. For that, scale the primary vertically, or look at [DynamoDB](/docs/architecture/2-databases/nosql).

## What it costs

More instances, a load balancer billed by the hour and by use, and more parts to understand. Worth it when the site must stay up or traffic swings. Overkill for a one-evening workshop app.
