A NoSQL database drops some relational features to be faster and easier to scale. Amazon DynamoDB is the AWS one most people meet first. It supports key-value and document data.

## How DynamoDB stores data

- A **table** holds **items**. An item is like a row, but items in the same table do not need the same attributes.
- Every item has a **primary key**. Either a **partition key** alone, or a partition key plus a **sort key**.
- DynamoDB hashes the partition key to decide where the item lives. Items with the same partition key are stored together, ordered by the sort key.

For the sign-up app, a table keyed on `email` would work: one item per sign-up, found by email in one read. If the club ran many events, a composite key of event and email (pictured) keeps each event's sign-ups together.

## What is different from SQL

- **No joins.** You shape the data around the questions you will ask, often copying data into more than one item, instead of joining tables at query time.
- **Design the keys first.** Fast reads come from knowing the key. Searching on other attributes needs an index or a full scan.
- **No servers.** There is nothing to size, patch or upgrade, and no maintenance window. In on-demand mode you pay per request, and an idle table costs nothing for throughput.

## When it fits

- You always look data up by a known key: a user ID, a session, a cart.
- Traffic is high or spiky, and you want it to scale without planning.
- It pairs with AWS Lambda in [4. Serverless](/docs/architecture/9-serverless).

## When it does not

- You need ad hoc queries, reports or joins across many tables. Use a relational database.
- You do not know yet how the data will be read. Start relational; move a hot path to DynamoDB later if you need to.
